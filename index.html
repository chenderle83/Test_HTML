Git und GitHub: Was ist der Unterschied?

Beide gehören zusammen, erfüllen aber unterschiedliche Aufgaben.

1

Git speichert Versionen

Git läuft auf deinem Computer. Es protokolliert Änderungen und erlaubt dir, frühere Zustände wiederzufinden.

2

GitHub verbindet Teams

GitHub speichert Git-Repositories online und ergänzt Zusammenarbeit, Reviews, Issues, Rechteverwaltung und Automatisierung.

3

Das Repository ist das Projekt

Ein Repository – kurz Repo – enthält Dateien, Versionsgeschichte und meist auch Dokumentation und Aufgaben.

Der typische Ablauf für Einsteiger

Arbeite in einem eigenen Branch. So bleibt main stabil und deine Änderung kann vor dem Zusammenführen geprüft werden.

CloneProjekt laden
BranchArbeitszweig erstellen
CommitÄnderung speichern
PushZu GitHub senden
Pull RequestPrüfen und mergen

Beispiel im Terminal

# 1. Repository von GitHub herunterladen
git clone https://github.com/name/projekt.git
cd projekt

# 2. Einen eigenen Branch erstellen
git switch -c feature/neue-startseite

# 3. Änderungen prüfen und für den Commit auswählen
git status
git add index.html

# 4. Einen nachvollziehbaren Zwischenstand speichern
git commit -m "Startseite verständlicher gestalten"

# 5. Den Branch zu GitHub hochladen
git push -u origin feature/neue-startseite
Danach auf GitHub: Öffne einen Pull Request, beschreibe Ziel und Tests, lasse die Änderung prüfen und führe sie erst danach in main zusammen.

Was bedeutet „Pull“?

git pull holt neue Änderungen vom entfernten Repository und integriert sie in deinen aktuellen lokalen Branch.

git fetch

Lädt Informationen und Commits herunter, verändert deinen Arbeitsbranch aber noch nicht. Gut zum sicheren Prüfen.

git merge

Verbindet zwei Entwicklungsstände. Dabei kann ein zusätzlicher Merge-Commit entstehen.

git pull

Ist im Standardfall die Kurzform für fetch plus merge. Mit --rebase werden lokale Commits stattdessen auf die neuen Commits gesetzt.

Nicht verwechseln: Ein Pull Request lädt nichts herunter. Er ist die Bitte, einen Branch zu prüfen und seine Änderungen in einen anderen Branch zu übernehmen.

Die wichtigsten Begriffe

Suche nach einem deutschen oder englischen Begriff. Das Lexikon erklärt, was er im Arbeitsalltag bedeutet.

Repository (Repo)
Projektordner inklusive seiner vollständigen Git-Versionsgeschichte.
Clone
Lokale Kopie eines entfernten Repositorys auf deinem Computer.
Branch
Eigene Entwicklungslinie, die paralleles und sicheres Arbeiten ermöglicht.
Commit
Gespeicherter, beschrifteter Zwischenstand ausgewählter Änderungen.
Staging Area / Index
Auswahl der Änderungen, die in den nächsten Commit aufgenommen werden.
Push
Überträgt lokale Commits in ein entferntes Repository, etwa auf GitHub.
Pull
Holt entfernte Änderungen und integriert sie in den aktuellen Branch.
Fetch
Holt entfernte Änderungen, ohne den aktuellen Arbeitsbranch zu verändern.
Pull Request (PR)
Vorschlag, Änderungen prüfen und in einen Zielbranch übernehmen zu lassen.
Merge
Führt die Historien und Änderungen von Branches zusammen.
Rebase
Setzt Commits auf eine neue Basis und erzeugt eine geradlinige Historie.
Remote
Verknüpfung zu einer entfernten Kopie des Repositorys.
Origin
Üblicher Standardname für das Remote, von dem ein Repo geklont wurde.
Main
Üblicher Name des stabilen Hauptbranches eines Repositorys.
HEAD
Zeiger auf den aktuell ausgecheckten Branch beziehungsweise Commit.
Issue
Dokumentierte Aufgabe, Idee, Frage oder Fehlermeldung auf GitHub.
Fork
Eigene GitHub-Kopie eines fremden Repositorys für unabhängige Änderungen.
Merge-Konflikt
Git kann konkurrierende Änderungen nicht automatisch zusammenführen.
Tag / Release
Markierung eines festen Versionsstands, oft für eine Veröffentlichung.
CI/CD
Automatische Prüfungen, Builds und Auslieferungen nach Codeänderungen.

Keine passenden Begriffe gefunden.

Für Fortgeschrittene

Diese Arbeitsweisen halten die Historie verständlich und reduzieren Probleme in größeren Teams.

Merge oder Rebase?
  • Merge bewahrt die tatsächliche Verzweigung und ist sicher für gemeinsam genutzte Branches.
  • Rebase erzeugt eine lineare Historie, schreibt aber Commit-IDs neu. Nutze es bevorzugt auf deinem eigenen Branch.
  • Veröffentliche umgeschriebene eigene Branches nur mit git push --force-with-lease, niemals blind mit --force.
Einen aktuellen Feature-Branch vorbereiten 
git fetch origin
git switch feature/neue-startseite
git rebase origin/main
# Konflikte lösen, Dateien mit git add markieren, dann:
git rebase --continue
Gute Pull Requests
  • Behandle ein klar abgegrenztes Problem pro Pull Request.
  • Erkläre Motivation, Lösung, Tests und mögliche Risiken.
  • Halte Commits verständlich und entferne keine Schutzmechanismen.
  • Reagiere auf Review-Kommentare mit zusätzlichen Commits.
  • Merge erst, wenn automatische Prüfungen und Reviews erfolgreich sind.
Sicher rückgängig machen
  • git restore datei verwirft nicht vorgemerkte lokale Änderungen an einer Datei.
  • git restore --staged datei entfernt eine Datei aus der Staging Area, ohne ihre Änderung zu löschen.
  • git revert COMMIT erzeugt einen neuen Gegen-Commit und eignet sich für bereits veröffentlichte Historie.

Die kurze Merkliste

Vor der Arbeit

Aktualisiere deinen Stand, lies die Projektanleitung und erstelle einen eigenen Branch.

Während der Arbeit

Prüfe regelmäßig git status und erstelle kleine, verständlich benannte Commits.

Vor dem Merge

Teste deine Änderung, beschreibe den Pull Request und warte auf erfolgreiche Prüfungen.

Tipp: GitHub stellt unter GitHub Skills kostenlose interaktive Übungen bereit.
